## Q01. Flink DataStream 메서드 선택 (10점)

| 빈칸 | 정답 | 역할 |
|---|---|---|
| ___1___ | `get_execution_environment` | 실행 환경 생성 |
| ___2___ | `from_collection` | 리스트 → DataStream |
| ___3___ | `filter` | 조건에 맞는 원소만 유지 (수량 0 제외) |
| ___4___ | `map` | 원소 하나 → 원소 하나 (금액 계산) |
| ___5___ | `key_by` | 매장 기준 그룹화 |
| ___6___ | `execute_and_collect` | 작업 실행 + 결과 수집 |

- 실측 출력: `('gangnam', 6000)` → `('hongdae', 4500)` → `('jamsil', 15000)` → `('hongdae', 10500)` → `('gangnam', 10000)`
- `key_by().sum(1)`은 **최종값만이 아니라 들어올 때마다 중간 누적값**을 내보낸다. gangnam은 6000 → 10000 두 번 출력된다.
- `("gangnam", 2500, 0)`은 filter에서 빠지므로 결과에 없다. filter를 빼면 gangnam이 6000 → 6000 → 10000으로 한 줄 더 나온다.
- `execute_and_collect` 대신 `execute`를 쓰면 반복할 결과가 없다. 실행 계획만 보려면 `env.get_execution_plan()`.

## Q02. Spark RDD 메서드 선택 (15점)

| 빈칸 | 정답 | 이유 |
|---|---|---|
| ___1___ | `textFile` | 한 줄 = 원소 하나 |
| ___2___ | `flatMap` | 한 줄 → 여러 단어로 **펼침** (`map`이면 리스트가 원소가 됨) |
| ___3___ | `map` | 단어 하나 → 정리된 단어 하나 |
| ___4___ | `filter` | 길이·불용어 조건 |
| ___5___ | `reduceByKey` | 같은 키의 값을 합산(파티션 안에서 먼저 부분 합) |

- 실측: `delivery=3, fast=3, great=3, price=3, packaging=2, UNIQUE=14`
- 3회 단어 4개가 동률이라 단어 오름차순, 2회는 packaging·quality 중 packaging이 5번째.
- `strip(".,!?")`이 없으면 `clean.`·`price!`처럼 문장부호가 붙은 단어가 따로 세어진다(제공 코드에 이미 포함).
- `groupByKey().mapValues(sum)`도 결과는 같지만 빈칸 뒤 `(lambda a, b: a + b)`는 두 값을 받는 함수이므로 `reduceByKey`만 맞는다.

## Q03. 지연 평가와 Spark UI (10점)

- 코드 수정 없음. 채점 포인트는 캡처 3장: **Enter 전 Jobs 0개**, **Enter 후 Completed Jobs 2개(collect, count)**, 터미널의 `RESULT [6, 12, 18, 24, 30]`, `COUNT 5`.
- 실측(Spark REST API로 확인): Enter 전 0개 → 후 2개 `collect at lazy_check.py:18`, `count at lazy_check.py:19`.
- 이유: `map`·`filter`는 Transformation이라 계산 계획(계보)만 만든다. `collect`·`count` 같은 Action이 호출될 때 Job이 만들어져 실행된다. Action마다 Job이 하나씩 생기므로 2개다(캐시하지 않았으므로 count 때 다시 계산).
- 주의: 출력되는 UI 주소의 호스트명이 컴퓨터 이름일 수 있다 → 브라우저에서는 `localhost:4040`. 다른 Spark 프로그램이 4040을 쓰고 있으면 4041.

## Q04. 카테고리 매출 SQL (15점)

```python
df.createOrReplaceTempView("sales")
query = """
    SELECT category,
           COUNT(*) AS order_count,
           SUM(price * qty) AS revenue
    FROM sales
    WHERE status = 'DONE'
    GROUP BY category
    ORDER BY revenue DESC, category ASC
"""
```
- 실측: book 2·84000 / beauty 1·43000 / toy 3·43000 / food 2·30000, `ROWS=4`
- 감점 포인트: `WHERE` 누락(CANCEL 포함 시 food 70000, book 99000으로 순위 변동), 별칭이 `order_count`·`revenue`가 아님, 2차 정렬 누락(beauty·toy 동률 순서 불확정), 뷰 이름 불일치(`Table or view not found`).
- `WHERE`는 `GROUP BY` 이전에 행을 거른다. 집계 결과로 거를 때는 `HAVING`.

## Q07. 포인트 잔액 상태 (15점)

```python
def apply_point(balance, event_type, amount):
    if event_type == "EARN":
        return balance + amount
    if event_type == "USE" and balance >= amount:
        return balance - amount
    return balance

def open(self, runtime_context):
    descriptor = ValueStateDescriptor("balance", Types.INT())
    self.balance_state = runtime_context.get_state(descriptor)

def process_element(self, value, ctx):
    current = self.balance_state.value()
    if current is None:
        current = 0
    new_balance = apply_point(current, value[1], value[2])
    self.balance_state.update(new_balance)
    yield value[0], value[1], new_balance
```
- 실측 7줄: u1 500 → 300 → **0**(잔액과 같은 300 사용 허용) / u2 300 → **300**(400 사용 거부) → 400 → 0, `COUNT=7`. 다른 입력(`a USE 10` → 0 유지 …)으로 바꿔도 정상 동작 확인.
- 핵심: `ValueState`는 **키(회원)마다 따로** 저장된다. `key_by` 뒤에서만 키별 상태를 쓸 수 있다. 처음 접근한 키의 상태는 `None`이므로 0으로 시작한다.
- `return`이 아니라 `yield`(출력이 0개 이상일 수 있는 process 함수). 상태를 `update`하지 않으면 매번 0에서 시작한다.
- 상태를 일반 파이썬 변수(`self.total`)로 두면 키가 섞이고, 체크포인트에도 포함되지 않는다 → 문항 8과 연결.

## 부록: 추가 서술형 연습 (실습 기반, 채점 대상 아님)

1. `groupByKey().map(합계)`와 `reduceByKey(합계)`의 결과는 같지만 셔플되는 데이터 양이 다른 이유를 설명하시오. 평균을 reduceByKey로 구하려면 값을 어떤 형태로 바꿔야 하는가? → 파티션 안에서 부분 합(combiner) 후 이동 / `(합, 개수)` 튜플로 누적한 뒤 마지막에 나눔 (ws5-5, 1111 p28~31)
2. `repartition(2)`와 `coalesce(2)`의 셔플 여부와, 파티션 수를 늘릴 때 coalesce가 어떻게 되는지 쓰시오. → repartition은 셔플로 균등 재분배, coalesce는 기본 셔플 없이 합침(불균등 가능), 늘리려면 `shuffle=True` 필요 (ws5-4, 1111 p37~40)
3. 5초 텀블링 창, 워터마크 지연 1초, 허용 지연 3초에서 이벤트 시각 2000ms 데이터가 워터마크 9000ms 이후에 도착하면 어떻게 처리되는가? → 창 [0,5000)의 정리 시점(5000-1+3000=7999) 이후이므로 창에 반영되지 않고 side output(TOO LATE)으로 분리 (hw3-4)
